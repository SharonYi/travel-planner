# 案例复盘:巴厘岛 + 双火山 12 日行程

> 一次真实的人机协作行程规划:从最初的「3 人小团、D1–D10、双火山+科莫多+潜水」到最终的「4 人小团、Safari+瀑布+Bromo+佩妮达+巴厘岛+河内中转」,历经 **20+ 轮人工反馈迭代**、一次航变、一次火山山火、十余次酒店改订。
>
> 本文档完整记录每轮反馈、Agent 的应对、以及沉淀出的方法论。最终交付物见 [../itinerary/bali-2026/index.html](../itinerary/bali-2026/index.html)。

## 0. 初始输入

```
时间: D1–D10(10 天,具体日期已脱敏)
人员: 3 人小团(后变 4 人)
硬约束: D1–D3 三天包车司机已订(入境机场 → 渡轮码头)
意愿: 巴厘岛 + 科莫多(可放弃),需要潜水(体验潜)
```

## 3. 方法论沉淀(给 Agent 的十条规则)

1. **硬约束先于偏好**:已订的包车/机票/酒店是不可变量,围绕它们规划
2. **多方案 + 对比表**:关键分歧点给 2–3 版,量化对比(强度/在途/成本/体验),推荐但不替用户决定
3. **在途时间显式化**:每段交通标方式+耗时,算累计值;「一天在路上超 6h」要主动预警
4. **证件与能力 gating**:潜水证、徒步体能、驾照直接决定可选项集合
5. **状态机管理预订**:✓已订 / 建议预订 / 待退 / 备选,每次变更同步所有关联表格
6. **风险 = 概率 × 影响 + 决策点**:给 A/B 预案和「什么时候必须拍板」的日期,不为小概率推翻全局
7. **冲突主动上报**:用户的新想法与已订事实冲突时,先指出再执行
8. **交付单文件 HTML**:零依赖、响应式、兼容旧内核(避免 CSS 变量等非必要现代特性)、可打印
9. **签证/政策类信息要时效标注**:给出办理时间线(提前量),注明「以官方为准」
10. **简洁**:每轮回复一个主题,信息密度优先于信息总量;用表格替代段落

## 4. 关键转折点复盘

**转折 1:砍科莫多(迭代 2)**
用户说「没有潜水证、只体验潜一天」——科莫多的核心价值 80% 在强流潜水。Agent 没有勉强保留「打卡式科莫多」,而是直接建议放弃。**目的地是体验的载体,不是目的本身。**

**转折 2:航变 + 改期(迭代 16–17)**
外部事件(航变)触发重规划。多出的一天没有用来加新目的地(用户曾问科莫多还能不能塞),而是补回被压缩的乌布放松日。**行程质量的瓶颈往往不是「玩得不够多」,而是「喘不过气」。**

**转折 3:Ijen 山火(迭代 24–26)**
火山关闭是概率事件(历史年均有关闭窗口)。Agent 给出量化评估 + Plan B + 决策时间点,最终用户确认关闭后整体重写爪哇段(Safari+Sewu+Bromo+飞行),原渡轮方案作废并进入退订流程。**风险预案的价值在于:决策日到来时,方案已经想好,只需执行。**

## 5. 统计

- 反馈轮次:28+ 轮
- 方案大版本:5 版(初版/V1V2V3 三选/细化版/航变版/最终版)
- 外部事件:1 次航变、1 次火山山火、多次酒店改订
- 交付物:1 个单文件响应式 HTML(~30KB),含 6 张表 + 河内中转行程
